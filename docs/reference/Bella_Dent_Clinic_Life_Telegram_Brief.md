# PROJECT BRIEF — Bella Dent «Жизнь клиники» + Telegram Automation

Ты получаешь существующий сайт стоматологической клиники **Bella Dent**. Сайт уже разработан и визуально готов. Необходимо не переделывать его, а расширить функциональность.

Это уже не просто добавление HTML-секции. Нужно создать небольшую **автоматизированную content-management систему**, которой сотрудники клиники смогут пользоваться через Telegram, вообще не заходя в код сайта, GitHub, Cloudinary, Google Sheets и другие технические сервисы.

Главная идея:

```
```

```
Сотрудник клиники
        ↓
Telegram Bot
        ↓
Backend / Orchestrator на Railway
        ↓
Media Agent → Cloudinary
        ↓
Publishing Agent → Google Sheets
        ↓
API
        ↓
Сайт Bella Dent
```

Параллельно этот же backend должен принимать заявки с формы сайта и отправлять их администраторам в Telegram.

---

# 1. Главная бизнес-задача

На существующий сайт добавляется секция:

**«Жизнь клиники»**

В ней всегда отображаются **максимум 3 актуальные новости**.

Сотрудники клиники должны иметь возможность самостоятельно добавлять новости через Telegram.

Никакого:

-  редактирования HTML; 
-  GitHub; 
-  ручной работы с Cloudinary; 
-  загрузки файлов в папки сайта; 
-  изменения JSON вручную; 
-  повторного деплоя сайта ради новой новости. 

Для сотрудника весь процесс должен занимать примерно минуту.

---

# 2. Важнейшее правило: на сайте всегда только 3 новости

Это принципиальное требование.

Например:

```
```

```
Добавлена новость A
→ на сайте: A

Добавлена новость B
→ на сайте: B, A

Добавлена новость C
→ на сайте: C, B, A

Добавлена новость D
→ на сайте: D, C, B
```

При публикации `D` новость `A` должна автоматически покинуть активную выдачу.

То же самое дальше:

```
```

```
Добавлена E

Сайт:
E
D
C
```

Таким образом:

> **Количество активных новостей никогда не должно превышать 3.**

### Важно

Не нужно физически удалять старую новость из Cloudinary или уничтожать данные.

Правильнее реализовать **архивирование**.

Например:

```
```

```
A → archived
B → published
C → published
D → published
```

Это намного безопаснее, чем физическое удаление.

Таким образом, старая публикация исчезает с сайта, но информация остаётся в системе и при необходимости может быть восстановлена.

# 3. Как сотрудник клиники добавляет новость

Создаётся отдельный Telegram-бот.

После `/start` сотрудник видит, например:

```
```

```
Bella Dent — управление сайтом

[ ➕ Добавить новость ]
[ 📰 Активные новости ]
[ 📁 Архив ]
```

Основной сценарий:

## Шаг 1

Пользователь нажимает:

**➕ Добавить новость**

Бот отвечает:

> Отправьте заголовок новости.

Пользователь:

> К нам приехала съёмочная группа телеканала

---

## Шаг 2

Бот:

> Теперь отправьте описание новости.

Клиент может просто скопировать уже существующий текст из Instagram.

---

## Шаг 3

Бот:

> Отправьте фотографию или видео.

Пользователь просто кидает обычное фото или видео непосредственно в Telegram.

Никаких ссылок на Cloudinary сотрудник создавать не должен.

---

# 4. Что происходит с фотографией или видео

После получения файла работу забирает **Media Agent**.

Он должен автоматически:

```
```

```
Получить Telegram file_id
↓
Получить файл
↓
Проверить тип файла
↓
Подготовить его к загрузке
↓
Отправить через Cloudinary API
↓
Получить secure_url
↓
Получить cloudinary_public_id
↓
Сохранить результаты
```

Например пользователь отправил обычное фото.

Cloudinary возвращает:

```
```

```
https://res.cloudinary.com/.../image/upload/...
```

На сайте используется уже этот URL.

Сам файл **не хранится внутри проекта сайта**.

Это принципиальная часть архитектуры.

---

# 5. Зачем Cloudinary

Нельзя превращать репозиторий сайта в хранилище фотографий и особенно видео.

Схема должна быть:

```
```

```
Сайт
→ хранит только данные/URL

Cloudinary
→ хранит сами фото и видео
```

Таким образом:

-  проект сайта не разрастается; 
-  Git-репозиторий не заполняется тяжёлыми файлами; 
-  медиа отдаётся специализированной CDN; 
-  изображения можно автоматически оптимизировать; 
-  видео не создаёт нагрузку на сам сайт; 
-  можно добавлять новости годами без постоянного роста размера frontend-проекта. 

Для изображений использовать оптимизированную Cloudinary delivery-схему, responsive delivery и автоматический подход к формату/качеству там, где это возможно.

# 8. Publishing Agent

После `✅ Опубликовать` должен запускаться publishing workflow.

Он:

1.  создаёт уникальный ID новости; 
2.  фиксирует дату/время; 
3.  записывает данные в Google Sheets; 
4.  выставляет `status = published`; 
5.  проверяет количество `published`; 
6.  если их стало больше трёх — находит самую старую; 
7.  переводит её в `status = archived`; 
8.  инвалидирует/обновляет API-кэш, если он используется; 
9.  проверяет, что API возвращает ровно три последние публикации; 
10.  отвечает пользователю: 

```
```

```
✅ Новость опубликована.

Сейчас на сайте:
1. Новость D
2. Новость C
3. Новость B

Новость A автоматически перенесена в архив.
```

# 10. Как сайт должен получать новости

Не вставлять Google credentials непосредственно во frontend.

Предпочтительная архитектура:

```
```

```
Website
↓
GET /api/news
↓
Railway Backend
↓
Google Sheets
```

Endpoint:

```
```

```
GET /api/news
```

должен возвращать **только три опубликованные новости**, отсортированные:

```
```

```
published_at DESC
```

Пример:

```
```

```
[
  {
    "id": "n004",
    "title": "...",
    "description": "...",
    "mediaType": "image",
    "mediaUrl": "...",
    "instagramUrl": "...",
    "publishedAt": "..."
  }
]
```

Даже если в Google Sheets находится 200 архивных публикаций, frontend получает только три активных.

Не создавать новый визуальный язык.

Новая секция должна выглядеть так, будто она **изначально была частью существующего Bella Dent**.

Название:

Максимум:

**3 карточки.**

Карточка содержит:

```
```

```

Дата
Заголовок
Описание
Instagram-ссылка, если она существует
```

Desktop и mobile должны использовать существующие:

-  шрифты; 
-  цвета; 
-  border-radius; 
-  ширины container; 
-  spacing; 
-  кнопки; 
-  typography hierarchy; 
-  hover/animation patterns. 

Перед реализацией coding-agent должен исследовать существующий frontend и переиспользовать дизайн-токены сайта, а не приблизительно придумывать их заново.

# 13. Railway

Backend и Telegram Bot должны работать на Railway постоянно.

Предпочтительно один сервис:

```
```

```
Node.js backend
├── Telegram webhook
├── News API
├── Lead API
├── Cloudinary integration
├── Google Sheets integration
└── orchestration logic
```

Для Telegram в production предпочтительно использовать webhook через публичный Railway URL.

Все секреты хранятся только через Railway Variables.

Например:

```
```

```
TELEGRAM_BOT_TOKEN=
TELEGRAM_ADMIN_IDS=

CLOUDINARY_CLOUD_NAME=
CLOUDINARY_API_KEY=
CLOUDINARY_API_SECRET=

GOOGLE_SHEET_ID=
GOOGLE_SERVICE_ACCOUNT_JSON=

SITE_ORIGIN=
```

Никаких секретов во frontend и GitHub.

# 17. Security

Обязательно предусмотреть:

-  whitelist Telegram ID администраторов; 
-  Cloudinary API secret только backend; 
-  Google credentials только backend; 
-  проверку URL; 
-  sanitization текста; 
-  валидацию файлов; 
-  ограничение размера загружаемых файлов; 
-  CORS только для домена клиники; 
-  anti-spam для формы заявок; 
-  rate limiting; 
-  обработку ошибок Cloudinary; 
-  обработку ошибок Google Sheets; 
-  идемпотентность публикации, чтобы двойной клик не создавал две новости.

# 20. Что требуется от тебя как от следующего агента

На основании этого brief подготовь **максимально конкретное техническое ТЗ / implementation prompt для coding-agent**.

Coding-agent должен:

1.  сначала исследовать существующий проект и его стек; 
2.  не ломать текущий сайт; 
3.  определить существующий способ деплоя; 
4.  определить существующие дизайн-токены; 
5.  реализовать секцию `Життя клініки`; 
6.  создать Railway backend; 
7.  создать Telegram Bot; 
8.  подключить Cloudinary; 
9.  подключить Google Sheets; 
10.  реализовать rolling window ровно на **3 active news**; 
11.  реализовать архивирование четвёртой/старейшей новости; 
12.  реализовать форму заявок → Telegram; 
13.  добавить все необходимые environment variables; 
14.  написать setup-инструкцию; 
15.  добавить error handling; 
16.  протестировать весь сценарий end-to-end; 
17.  не объявлять задачу завершённой без фактической проверки Telegram → Cloudinary → Sheet → API → Website. 

**Ключевой acceptance criterion:**

```
```

```
A → сайт A
B → сайт B,A
C → сайт C,B,A
D → сайт D,C,B + A archived
E → сайт E,D,C + B archived
```

И всё это должно происходить **без изменения кода или повторного деплоя сайта при каждой новой публикации**.
